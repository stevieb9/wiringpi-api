# B4 — full assessment: non-blocking drain of the results channel

**Status: CLOSED — won't-do (author decision, 2026-06-11).** Kept as the rationale
of record; reopen only on a concrete need to stream large values through
`{results}`. The sharp *corruption* facet was split off and fixed as **B10**
(oversized `{shared}` values are dropped, not partially written). What remained in
B4 is narrower: making `read()` on the **`{results}`** channel truly non-blocking
regardless of return size — and that rewrite is the thing being declined here. The
4 KB limit stays *documented*.

---

## TL;DR recommendation

**Leave B4 deferred (documented-only) unless a concrete need for large return
values appears.** For this library's actual domain the issue is, in practice,
never hit; the worst case is a brief responsiveness delay, not corruption or data
loss; and the fix — while standard — is the only medium-risk change left in an
otherwise-solid path. Do it only if you decide to *support* large (>4 KB, and
realistically >256 KB) returns through `results` as a first-class use case.

Considerations below are ordered by that recommendation: the case for stopping
first, then the case for doing it and how.

---

## The facts (measured on this Pi, 2026-06-11)

| Fact | Value | Source |
|------|-------|--------|
| `PIPE_BUF` (atomic-write threshold) | **4096 bytes** | `POSIX::PIPE_BUF()` |
| Default pipe capacity | **262144 bytes (256 KB)** | `fcntl(F_GETPIPE_SZ)` |
| Results pipe resized? | **No** — `F_SETPIPE_SZ` is applied only to the interrupt self-pipe (`_apply_interrupt_buffer`, `API.pm:822`), never `$res_w`/`$val_w` | code read |
| Results writer | **Blocking** `syswrite` (`API.pm:712`, `1077`) | code read |
| Reader | `select(…,0)` gate then a **blocking** `_read_exact` of a length-framed record (`BackgroundInterrupt.pm:22-41,85-96`) | code read |

Portability note: `PIPE_BUF` is 4096 on Linux universally. Pipe **capacity**
varies — many Linux systems default to 64 KB; this Pi reports 256 KB. The
capacity matters for *how long* a stall lasts, not *whether* one can occur.

---

## Mechanism — exactly when, and how badly, `read()` can block

The reader assumes that once `select()` reports the pipe readable, the whole
length-framed record is present, then does a blocking `_read_exact`.

- **Record ≤ `PIPE_BUF` (4096 B):** a pipe write of ≤ `PIPE_BUF` is atomic — the
  kernel makes all the bytes appear together. So `select()`-readable *does* imply
  the whole record is buffered, and `_read_exact` never blocks. **Safe.**
- **Record > 4096 B:** the write may be split by the kernel, so `select()` can
  fire when only part of the record is buffered. `_read_exact` then blocks on its
  next `sysread` until the remaining bytes arrive.

Severity of that block, grounded in the numbers above:

1. **No corruption, no loss, no deadlock.** Single writer, bytes arrive in order;
   the parent and child make mutual progress; if the child dies mid-record the
   write end closes and `_read_exact` returns `undef` (that value is cleanly
   lost, nothing else). The only cost is latency.
2. **4 KB – 256 KB returns:** the child's blocking `syswrite` of the whole frame
   into a 256 KB pipe completes in one fast call (room available), so the window
   in which the parent can catch a *partial* record is tiny — the stall is
   typically sub-millisecond. Technically possible, practically negligible.
3. **> 256 KB returns (> pipe capacity):** the child's `syswrite` itself blocks
   (pipe full) and the record shuttles through in capacity-sized chunks; `read()`
   blocks for the whole transfer. This is the only regime that produces a
   *noticeable* stall (and it scales with size — a multi-MB return is a real,
   visible delay).

So the true "meaningful delay" threshold is the **pipe capacity** (256 KB here,
64 KB on many systems), not the 4 KB atomicity threshold. The 4 KB figure is the
point above which a stall is *theoretically possible*; the capacity is the point
above which it is *practically observable*.

Where a stall hurts most: **event-loop integration** (`select` on `$w->fh`, then
`read()`). A blocking `read()` freezes the caller's loop for the stall's
duration, so other events / interrupt servicing wait. For sub-ms stalls this is
invisible; for multi-hundred-KB returns it is not.

## Most likely use-case scenario — and will the issue ever be hit?

**What workers/handlers actually return here.** This is a Raspberry Pi GPIO
library. `background_interrupt`/`worker` bodies return things like a pin level
(`0`/`1`), an ADC reading, a short sensor value, or a brief status string — tens
of bytes at most. The `{results}` channel is opt-in; many programs don't use it
at all, and those that do stream small scalars.

**To hit even a theoretical block** a user must return > 4 KB from a handler/
worker body — i.e. serialize a large structure through an interrupt results
channel. **To hit a *noticeable* block** they must return more than the pipe
capacity (256 KB here), *and* be servicing the channel in a latency-sensitive
loop. Returning hundreds of KB through an ISR results pipe is outside the
channel's intended purpose (bulk data belongs in a file/socket/dedicated IPC).

**Verdict:** for the library's real domain, the issue is **effectively never
hit.** It is reachable only by atypical-to-misuse payloads, the failure mode is a
delay (now that B10 removed the corruption path), and the 4 KB limit is already
documented as a known constraint. A user who reads the POD and keeps returns
small is unaffected; a user who doesn't will, at worst, see an occasional hiccup
proportional to how far past the pipe capacity they went.

## Cost / risk of doing B4

The only correct fix is a **non-blocking, accumulating reader** (pipe peeking is
not an option — pipes don't support `MSG_PEEK`, and you can't un-read the 4-byte
length once consumed; increasing pipe *capacity* doesn't help because the 4 KB
atomicity threshold is independent of capacity).

Shape of the change:
- Set the results read fh `O_NONBLOCK`.
- Keep a per-handle byte buffer in `$self`; on each `read()`, `sysread` whatever
  is available, append, then parse complete length-prefixed frames out of the
  buffer (the 4-byte length itself can split across reads), returning one frame
  and retaining the remainder. Return `undef` until a whole frame is buffered.
- Handle `EAGAIN`/`EWOULDBLOCK` (nothing ready), `EINTR` (retry), and EOF
  (child gone) without blocking.
- `Worker::value()` shares `_read_exact`; it would move to the same buffered
  model (and must keep its lossy "drain to latest" semantics).

Risk profile: **moderate, but fully testable off-board** (t/88 shows the shared
path is exercisable without hardware/threads). The accumulate-and-parse reader is
a standard pattern; the real risk is *regressing the well-exercised small-payload
path* (t/77, t/85) and the edge cases (partial length prefix, multiple queued
frames, EOF mid-frame, the existing `select()` gate becoming redundant). It is
more than a one-liner and touches the hottest part of the IPC path.

Test plan if implemented: a > `PIPE_BUF` framed return must not block `read()`;
a record split across multiple `sysread`s reassembles correctly; multiple queued
records drain in order; a partial 4-byte length prefix is handled; EOF mid-record
returns `undef`; `value()` still returns lossy-latest; and the existing
small-payload behaviour is unchanged.

---

## Options, prioritised by recommendation

1. **(Recommended) Leave deferred / documented.** Keep the 4 KB POD caveat (B4
   doc work is already done) and B10's corruption guard. Close the audit. Cost:
   nothing. Residual risk: a sub-ms-to-ms `read()` stall *only* for atypical
   >4 KB returns, noticeable only for >256 KB. Acceptable for the domain.

2. **Tighten the documentation only** (cheap, optional). Restate the limit at the
   `read()`/`{results}` POD in terms users can act on: "keep returns small; for
   bulk data use a file/socket." No code change. Marginally improves the
   already-documented state.

3. **Do the full non-blocking + accumulating reader** (the real fix). Choose this
   only if supporting large `{results}` returns becomes a real requirement, or a
   hard non-blocking guarantee for event-loop users at any payload size is
   wanted. Moderate, testable, but the only medium-risk change left in a solid
   path — not justified by any current use case.

**Explicitly rejected as non-fixes:** enlarging the results pipe via
`F_SETPIPE_SZ` (capacity ≠ atomicity; a >4 KB write can still split, so the
parent can still catch a partial record); any `MSG_PEEK`/peek-the-length scheme
(unsupported on pipes).
